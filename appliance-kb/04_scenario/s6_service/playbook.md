# s6 报修建单 · 场景剧本

## 这个场景本质是表单，不是问答

用户要的是"有人来修"，不是"听你解释"。所以：

- 知识只负责两件事：**该收哪些字段**、**这些字段为什么要**
- 其余全部交给工单系统

判据：这个场景答得好不好，看的是**工单一次派成率**，不是回答字漂亮。

## 建单必填八项（缺一项，师傅就要多打一通电话）

| 字段 | 为什么必需 | 缺失后果 |
|---|---|---|
| 型号 | 决定带什么备件、查什么代码规则 | 带错件，二次上门 |
| 故障现象（用户原话） | 决定派什么工种的师傅 | 派错人 |
| 已做过的自查 | 避免重复引导 | 用户体验崩 |
| 联系人 + 电话 | 上门联系 | 无法派单 |
| 地址（含楼层/电梯） | 决定是否高空、是否上楼费 | 到楼下才发现进不去 |
| 期望时间 | 排期 | 反复改约 |
| 是否保修内 | 决定是否收费、走哪套流程 | 现场扯皮 |
| 安全标记 | 命中 red lines 的加急 | 延误风险 |

## 派单前的三个校验

1. **型号是否已确认**——只有"空调"两个字不能建单
2. **是否已有未完结工单**——重复建单会让用户被两个师傅联系
3. **是否需要备件**——按 `parts_catalog.yaml` 预判，需备件的要标注，否则师傅空手来

## 进度查询只报节点，不报时间

```
已受理 → 已派单 → 工程师已联系 → 已上门 → 维修中 → 已完成
```
- 可以说的："已经派单了，师傅会在 24 小时内联系您"
- 不能说的："师傅明天上午 10 点一定到"

## 三条边界

1. **不承诺上门时刻**，只承诺联系窗口
2. **不在未确认型号/现象前建单**——垃圾工单比不建单更贵
3. **命中安全红线**（漏水、跳闸、焦味）的，加急标记 + 建议停机，不能按普通单排期

## 建单话术（一次问全，别挤牙膏）

```
我帮您登记一下，麻烦确认这几项：
1. 机器型号（机身侧面标签上的）
2. 具体什么情况
3. 上门地址，几楼，有没有电梯
4. 联系人和电话
5. 什么时间方便
```

## 品类差异速查（2026-10-23 新增）

建单本身不复杂，复杂的是**这个品类到底有没有"上门"这回事**：

| 品类 | 服务模式 | 建单时必须问的额外信息 |
|---|---|---|
| 空调 | 上门 | 楼层、有无电梯、外机位、是否需要高空作业 |
| 洗衣机 | 上门 | 有无地漏/水龙头、最窄门宽与转角、是否新装机（关系到运输螺栓） |
| 电饭煲 | **送修 / 寄修为主**，上门属部分区域的增值服务 | 所在城市有没有服务网点；是否只需补件（内胆/密封圈可寄） |

电饭煲这一行最容易翻车：话术里出现"师傅 24 小时内联系您上门"，
而当地其实只有寄修点，用户会在第二天投诉"没人联系"。

## 配件单与整机单要分开

电饭煲的内胆、密封圈、蒸汽阀、量杯属于**可寄件**，走的是配件单，
不必整机送修；洗衣机/空调的备件则通常要上门更换（涉及拆装与电气）。
判错的后果：用户把整机寄过来，只为换一个 20 元的密封圈。

配件是否可单独购买、能否自己装，查 `05_brand_ref/{brand}/parts_catalog.yaml`；
价格查 `fee_schedule.yaml`（注意是区间，不是报价）。

# s2 安装咨询 · 场景剧本（通用）

> 本文只写**三个品类都成立**的东西。品类差异见 `by_appliance/`：
> - `air_conditioner.md` —— 电/位/管三查，最复杂的一类
> - `washer.md` —— 电/水/排水/门四查
> - `rice_cooker.md` —— 免安装，只查插座/放置/开箱验收
>
> **先判品类，再决定要不要走"安装"这条线。** 电饭煲根本不存在安装，
> 把空调的"高空费/加长铜管"套上去，用户会以为我们在编项目收费。

## 这个场景的两条主线

1. **能不能装**（技术判定，答错会白跑一趟或留下安全隐患）
2. **要花多少钱**（费用判定，答错就是投诉）

这两件事必须分开回答，混在一起说会让用户只记住金额、忽略条件。

## 先做一次分流：这个品类到底要不要装

| 品类 | 是否要上门安装 | 用户真正需要确认的 |
|---|---|---|
| 空调 | 必须 | 电（专用回路）、位（墙面/外机位）、管（长度与高度差） |
| 洗衣机 | 必须 | 电、进水、排水、门宽与转角 |
| 电饭煲 | **不需要** | 插座能不能带得动、放哪儿不能放、开箱验什么 |

分流错了，后面全错。用户问"电饭煲安装要注意什么"，正确答案是
"这类产品不用安装，插上电就能用，您只需要确认插座和放置位置"，而不是给一段装机清单。

## 能不能装：按品类的"几查"

空调三查（电/位/管）、洗衣机四查（电/水/排水/门）的具体指标见对应 `by_appliance` 文件。
共同的判断原则：

- 全部条件满足才能说"可以装"。任一项不满足，给**具体原因 + 替代方案**，不是笼统说"装不了"
- 硬指标必须按型号查 `03_product/{appliance}/{brand}/{model}/install.yaml`，不能记平均值
- 涉及安全的（最小房间面积、燃气/R32 限制、承重、漏保）不达标必须拒绝，不许"先装了再说"

## 要花多少钱：只说项目，不报总价

安装费的结构：**基础安装（多数含在售价里）+ 可能产生的辅材/服务费**。

可能产生的项目按品类完全不同（金额见 `05_brand_ref/{brand}/fee_schedule.yaml`）：

| 品类 | 有 | 没有（别乱报） |
|---|---|---|
| 空调 | 高空作业、加长连接管、支架、打孔、拆装防盗网、上楼费、远程费 | 加装水龙头、地漏改造 |
| 洗衣机 | 加长进水管/排水管、加装水龙头、地漏改造、拆门扩门洞、上楼费、远程费、叠放支架 | 高空作业费、加长冷媒管、支架费（挂墙那种） |
| 电饭煲 | 无安装费；只有保外维修、配件、寄修运费 | 高空作业、加长管、上楼费、安装费 |

**铁律**：
- 只报单价/区间，合计金额必须由"实际米数 × 单价 + 楼层判定"得出，不允许凭口算给总价
- 收费项要在**上门前**说清，不能等师傅到了再报
- 价格 `price_verified: false` 时，必须加"这是行业常见范围，以师傅现场按标准确认为准"
- 严禁把参考区间说成品牌标准价（"海尔规定 100 元一米"是错的，海尔没公布过金额）

## 预约流程（仅限需要上门的两个品类）

```
确认型号 → 确认地址可用性 → 收集联系人与期望时间 → 校验是否需前置整改（布线/移窗/物业报备）
→ 建预约单 → 告知"师傅会在 X 小时内联系"
```
- 不承诺具体上门时刻，只承诺"联系窗口"
- 需物业报备/需业主同意的，提前说，避免师傅到门口被拦

## 上门前给用户的确认清单（一次发全，别分五条消息）

空调/洗衣机通用骨架：

```
装前麻烦确认几件事：
1. 安装位置有插座吗（空调要单独一路；洗衣机需带地线）
2. 楼层和有没有电梯
3. 大概要走几米管（空调连接管 / 洗衣机进排水管）
```

再按品类追加：

- 空调：室外机位置、墙面材质、房间面积是否达标
- 洗衣机：水龙头接口型式与水压、排水去哪（地漏还是水槽）、最窄门宽与转角
- 电饭煲：不用发这份清单，发"开箱验收 + 插座 + 放置位置"三条就够

## 最容易出错的四个点

1. 把"最大加长长度"当"标配长度"——标配通常 3~5 米，超出部分才收费
2. 把"待机功率"当"运行功率"——选线看最大输入电流
3. 忽略最小房间面积——R32 机型 4㎡ 是安全下限，不达标必须拒绝
4. 移机、拆装旧机当成安装——都属于收费项目，要单独确认

第五条（2026-10-23 新增）：**把需要安装的品类和免安装的品类混为一谈**。
电饭煲回答里出现"安装费""上门装机"，用户会直接质疑整套报价的可信度。
